## [01]-[STATE]

The repository's Nx setup had grown one target at a time with no owner per ecosystem:
- `tools/nx/` was one plugin for every host: markers for csproj, `.cs` scripts, Cargo, Blender, pyproject, tsconfig, Storybook, Vitest, Vite, Cloudflare, UXP and CEP, fonts, SEA, Claude hooks, and Xcode, plus root checks, sync generators, and release version actions
- `nx.json` held ~30 tool-named root targets (`lint:cargo-deny`, `typecheck:mypy`, `format:dotnet-format`, `upgrade:python`), brace-glob keys (`build{,:*}`), `targetDefaults` selected by tag strings (`tag:language:rust`, `tag:output:rhp`), `doppler run` and `$(minver …)` inside commands, and scattered `parallelism: false`
- `eng/` held one-off programs (release, upgrades, Blender packing, Adobe installs) and Rhino MSBuild host targets
- mise ran MCP servers as daemons and redirected tool state (`NX_WORKSPACE_DATA_DIRECTORY`, `HK_*`), root `lint:<tool>` targets wrapped one hk step each over the whole repository (`hk check --glob='**/*' --step=<tool>`) while hk's own pre-commit hook stayed off, and a sync generator copied one fact into eight files

It failed because it imagined each ecosystem instead of reading it. Swift modules came from a hand decode of `project.xcproj`, per-app facts sat in shell strings, and layouts were guessed where SwiftPM, Xcode, MSBuild, Cargo, and uv already state them. Every feature landed as another row in the nearest layer, each language reached through a different entry point, and CI never ran green because locks, caching, and parallelism were set by hand per target. The fix is to remove it all, accept a red tree, and rebuild each language on a focused plugin and corrected projects.

## [05]-[PLUGINS]

Every plugin starts from the ecosystem, never from this repository:
- Ecosystem first: every manifest, project, workspace, lock, and config file the toolchain reads, and the command printing each as data, is mapped under `docs/research/nx/<plugin>/` before code
- Prior art first: the official Nx plugin and the best community plugins set the model, ours changes only what quality, language, or performance demands
- Facts come from the toolchain's own output or its owner's decoder, never from file text, a glob convention, or a name (the old Python plugin decoded `uv.lock` by hand, which uv documents as no interface)
- The graph follows the tool's unit of work: projects where the tool has a unit, edges from declared dependencies, tasks at the level the tool builds and locks
- Configuration states each fact at its owner: where a tool's own configuration states a fact (Cargo `build.target-dir`, `.swift-format`, `[tool.ruff]`, `.editorconfig`), the plugin reads it back and declares no option for it; a plugin option exists only for a principle no tool configuration states (whether package macros are trusted), tool defaults when unset, never a per-tool or per-project field
- Values a project states (build settings, referenced files, schemes, platforms) are read from it and become task inputs, never restated in options
- Nx builds equal direct tool builds: nothing injected that the native tool or editor alone would miss, and build state shared with the editor and direct runs, so no caller rebuilds what another built
- CI-only behavior follows Nx's own `isCI()` (resolution locked to the lock file), never an option
- Caching and parallelism are the plugin's decisions from measured tool behavior, never `nx.json` rows:
  - Read-only targets cache on the files the tool reads, with `externalDependencies` stated (unstated, Nx hashes every npm package and reruns on any `pnpm-lock.yaml` change)
  - Writers and builds keeping incremental state in a shared directory stay uncached; Nx never restores a tool's own state folder
  - Tasks follow the tool's lock: one SwiftPM or Cargo invocation per lock holder (separate `cargo build -p` runs wait on one build-directory lock, 0.43 s against 0.28 s batched), a batch executor with `preferBatch` where the tool batches (`@nx/gradle`'s pattern), never `parallelism: false`, which holds every other task until it ends (two 1 s exclusive tasks and one normal task: 3.30 s against 1.25 s)
  - Tool versions hash through the pin and lock files the toolchain reads (`rust-toolchain.toml`, `.python-version`, `uv.lock`), never `runtime` inputs, which execute on every hash, cache hits included (a 2 s runtime input made a cache hit take 2.27 s)
- Edges decided by a shared file (root manifest, `[patch]`, tool configuration) are `implicit`: Nx keeps a static edge cached per source file and serves stale ones; external nodes from a lock carry a content hash, else a git dependency moving at one version never invalidates
- Performance lives in the code (one tool call per workspace, cached by a hash of inputs, options, and the plugin source) and in the graph, settled by measurement
- Each plugin works unchanged in an unrelated repository
- `nx.json` ends as one row per plugin with a few principle options, plus the shared release policy; no `targetDefaults`, `namedInputs`, tags, or parallel and cache fields for plugin targets
- No sync generators restating one fact into several files

Verbs, one set for every language and host, so an agent learns one way:
- `build`, `test`, `check`, `fix` on every project; `install` on every app and host project (macOS apps, Rhino and Grasshopper 2, Adobe, Blender, Unreal, local services); `deploy` on infrastructure stacks that apply without a version (repository, platform, non-production app stacks); `upgrade` on every ecosystem root; `nx release` ships
- File-level formatting and linting belongs to hk, project-level checking to the Nx plugins, each tool with one owner and neither calling the other (`docs/research/nx/hk.md`, owner decision): hk runs every formatter and per-file linter (rustfmt, ruff, ruff format, swift-format, Biome, shellcheck, shfmt, tombi, yamllint, actionlint, ast-grep) as steps in `.config/hk.pkl`, `hk fix` writing and `hk check` reading over changed files or `--all`, each tool's rules still in its own config file; measured, a changed file takes 39 ms through hk against 335 ms through Nx, an Nx cache hit on file checkers (293 ms) loses to hk re-running them (222 ms), and parallel Nx writers lost ruff fixes in 2 of 500 files where hk's file locks stayed exact; no Nx target wraps an hk step and no hk step calls Nx
- `check` reads: every project-level finding (compilers as type checkers, ty and mypy, clippy, Dylint, cargo-deny, .NET analyzers), failing on any finding through each checker's own strict switch, cached on its inputs; where the compiler is the type checker (Rust, Swift, C#) `check` covers that compile (`cargo clippy`, a `dependsOn` on `build`)
- `fix` writes the fixes that need a project model (`cargo clippy --fix`, `dotnet format`), one after another inside one task, uncached; formatters and per-file fixes are `hk fix`
- Each checker and writer is its own inferred target (`check--<tool>`, `fix--<tool>`), and `check`/`fix` are `nx:noop` targets with `dependsOn: ["check--*"]`/`["fix--*"]`: Nx 24 expands `dependsOn` globs (`tasks-runner/utils.js` `expandWildcardTargetConfiguration`), so several plugins add checkers to one project and each caches alone; users type the verb alone; the `nx:noop` aggregate declares the union of its dependencies' inputs, because `nx affected` selects a task by its own inputs and a change only a `check--<tool>` reads otherwise runs nothing for `-t check` (measured, `docs/research/nx/nx-usage.md`)
- Checkers come from what a project configures, never a fixed list: a plugin runs each checker the project's own files declare (a `[tool.ruff]` table, `[workspace.metadata.dylint]`, a `clippy.toml`, an `.editorconfig` rule set, an installed analyzer package), and a project declaring none gets none; hk steps follow the same rule through each tool's own config file
- Every finding is an error in every language and checker (ast-grep, Dylint, refurb, Biome, analyzers, lints alike), stated in each checker's own configuration (owner rule)
- One diagnostic path per language: severities live in each checker's own configuration, the editor and `check` report the same findings from it, and `check` fails on any finding through the checker's own strict switch; no build property flipping warnings into errors stands in for that policy (`TreatWarningsAsErrors`, `-Werror` rows)
- A distributable is `build` in its release configuration (Nx `configurations`, the mode mechanism); shipping is `nx release` running each project's inferred `nx-release-publish`; no `archive`, `pack`, or `publish` verb per host; `xcodebuild archive` then `-exportArchive` is how the Apple plugin builds in release mode, never a verb
- `install` puts the current local build into its host through the channel the host itself installs from, with no version, tag, or release: the same path a user's install takes, fed from the local build. Never a script imitating the host (the old macOS `install` quit the app, booted out its agents with `launchctl`, and copied it into `/Applications` with `ditto`)
- `upgrade` moves an ecosystem's dependencies to their newest releases through its own tool (`pnpm`, `cargo`, `uv`, `dotnet`, `swift package`, Xcode resolution), writing its catalog and lock; `nx migrate` upgrades Nx itself
- `eng/` existed for local install and upgrades across languages, as one-off programs mixed with release; each returns as a verb a plugin infers, never as a program

Nx is used through its own mechanisms, never around them, the basis every plugin is built on (`docs/research/nx/nx-usage.md` lists each old misuse and its native form):
- Variations are Nx's own forms: modes are target `configurations`, groups of targets are `dependsOn` globs, scope is `affected`/`--files`/`-p`, one-run switches are arguments after `--`; never a target, `targetDefaults` row, tag, or program per variation
- Each plugin owns its targets whole (command, inputs, outputs, caching, `dependsOn`, metadata); `nx.json` adds nothing to them

Entry points, scoped to the work at hand, never the whole repository by default:
- One project: `nx check <project>`, the inner-loop form, running that project alone; a file or folder: `nx affected -t check --files=<path>` runs its owning project plus every project depending on it (Nx's definition of affected: a shared Swift module's file also checks both apps, about 7 s of Xcode each), the form for verifying a change's reach; changed work: `nx affected -t check` from the git diff, which is also what CI runs; the whole repository: `nx run-many -t check`, deliberate only
- The same forms serve `fix`, `build`, `test`
- Arguments after `--` reach the tool for one run (a filter, a test name), never checker policy
- Editors report per-file findings from the same configurations through each tool's language server; the project is the smallest Nx unit
- Files: `hk fix` and `hk check` over changed files (`--all` in CI); how agents run them is reconsidered (the Stop hook was removed)
- Nx's own `nx format` formats through Prettier alone and is not used

- `nx.json` holds the shared policy alone: projects released independently, conventional commits, GitHub release creation, tag pattern, and `release.projects` or `release.groups` chosen by project, never by tag strings (`tag:output:nupkg`); non-JavaScript projects need those rows, since `nx release` selects only non-private `package.json` libraries by default
- Each language plugin supplies its ecosystem's two pieces, the pattern the official plugins use (`docs/research/nx/plugin-authoring.md` [04]):
  1. A `VersionActions` module writing the version where the ecosystem keeps it: Apple `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in `project.xcproj` through `XcodeProjectFormat`, Rust `Cargo.toml`, .NET `<Version>`, Python `pyproject.toml`; a Swift package has no version field, so tags carry it. The old `@rasm/nx/release` reported `0.0.0` and wrote nothing, with versions in MinVer shell strings
  2. An inferred `nx-release-publish` target per project for its ecosystem's registry: NuGet, crates.io, PyPI, npm
- Distribution past a registry (files on a GitHub release, Sparkle appcast, Rhino Yak, the Blender extension index, Adobe plugin packages, Unreal plugins, web deployments) is one distribution plugin reading the artifacts each language plugin declares as outputs, so every host distributes the same way; it owns both directions of each channel, publishing a release to it and `install` pulling a local build through it; no host's channel lives in shell strings or in `nx.json` (the old `publish` rows chained `doppler`, `gh release upload`, `generate_appcast`, `dotnet nuget push`, and Blender commands per tag filter)
