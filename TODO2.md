## [00]-[UNDERSTANDING]

What the rebuild taught, held by every session and every agent brief. Each line came from a mistake found and measured in this work (decision log [12], reports in `docs/research/nx/audit/`).

[SHAPE]: every package, plugin, and app is built as if published and used by others:
- Libraries are imported by strangers: it takes paths, ports, names, versions, locales, units, and policies from its caller or its own documented configuration, never from this repository's layout, environment variables, or machine; repository conventions (focus rules, output folders, naming, Atelier's protocol) live in the consumer, never in the library
- Shipped apps know themselves through its host API (`Bundle.main`, `process.execPath`) and keep user settings in their own preferences, never asking a developer's shell where it is (`ATELIER_PATH`, `MCP_LISTEN` were personal-tool habits)
- One fact, one owner: a version, port, image tag, license path, or tool location is stated once where its tool reads it and derived everywhere else (Atelier reported a version per layer; image tags stood in Pulumi, Compose, and a test suite; ports in mise, `.mcp.json`, and Codex)
- Public API states the domain: no foreign backend types leaking through signatures without a decision, no closed catalog a user would extend, an interface or context parameter where consumers plug in (one bound Rhino plug-in per process was a missing context)
- Packages ship what their users need and nothing of ours: dependency floors, metadata, license, readme; no runtime call to a workspace tool (`uv tree` inside `rasm-typography`), no binary only mise installs, no capability a dependency already provides rewritten by hand
- Packages hold a capability of their own, else they fold away: per-host folders holding only one app's handlers fold into that app

[EXTERNAL]: external processes are read and measured before any code or decision:
- Hosts and installers already do their job: UPIA installs Adobe plug-ins (Atelier's own installer and version compare were a misreading), Yak reads `<Version>` through `$version`, Blender reads a literal manifest version, Launch Services finds apps by bundle id, SwiftPM and Xcode share their default build folders with their editors, `nx release` versions and tags
- Tool behavior is learned from its source and docs at the installed version, never memory: Nx passes forwarded CLI arguments to every dependency (`params: "forward"` leaked), `globWithWorkspaceContext` skips gitignored files, Nx 24 still reads `maxCacheSize`, a plugin needs no `name` export, nextest has no config key for an empty run, Rhino loads one assembly per name per process, Blender forbids data access in `register()`, `.globalconfig` per-ID rows reach compiler warnings, `CodeAnalysisTreatWarningsAsErrors` selects the analyzers' own rule-set files
- Tools' own mechanisms beat any wrapper: Nx's per-plugin `exclude` over `.nxignore`, `tsc --project` over build mode and hidden `.tsbuildinfo`, SwiftPM's `experimental-install` and its folder on `PATH`, McNeel's committed `manifest.yml` with `$version`, PyPI's `Private :: Do Not Upload` classifier, `pluginsConfig["@nx/js"].projectsAffectedByDependencyUpdates: "auto"`
- Before removing a row, find its consumer; before restoring one, find its reader (the Rust pass deleted the test scaffolds, then the `bindeps` rows they needed; the `swiftpm/bin` `PATH` row was SwiftPM's own install folder, not a workaround)

[PROCESS]: how work runs:
- Order: research the ecosystem and the external processes, then design the shape, then code, then an adversarial review; a report is judged, never trusted (agents were wrong on `globWithWorkspaceContext`, the `name` export, the shared-file release bump, Darkroom's channel, and the root project's affected scope)

- Fixes land at the cause and owner, never as a workaround, guard, hidden output, or hand list; a fix that would need one is an owner decision

## [05]-[PLUGINS]

Every plugin starts from the ecosystem, never from this repository:
- Ecosystem and prior art first: every manifest, lock, and config file the toolchain reads, and the command printing each as data, mapped in the plugin's research folder; the official Nx plugin and the best community plugins set the model
- Facts come from the toolchain's own output or its owner's decoder, never from file text, a glob convention, or a name
- Graphs follow the tool's unit of work: projects where the tool has a unit, edges from declared dependencies (Xcode apps: build-phase files matched to declared outputs, [86]), tasks at the level the tool builds and locks
- Configuration states each fact at its owner; a plugin option exists only for a principle no tool configuration states; values a project states become task inputs
- Nx builds equal direct tool builds, sharing state with the editor and direct runs; CI-only behavior follows Nx's `isCI()`
- Caching and parallelism are the plugin's decisions from measured tool behavior: read-only targets cache on the files the tool reads with `externalDependencies` stated; writers of shared incremental state stay uncached; tasks follow the tool's lock (one cargo or SwiftPM process per lock holder, batch executors where the tool batches, never `parallelism: false`); tool versions hash through pin and lock files (`.config/mise.lock` for mise-installed tools), never `runtime` inputs
- Edges decided by a shared file are `implicit`; external nodes from a lock carry a content hash
- Each plugin works unchanged in an unrelated repository; `nx.json` ends as one row per plugin plus the shared release policy; no `targetDefaults`, `namedInputs`, hand-written tags, or parallel and cache fields; the one tag is `release`, inferred by each plugin where it sets up version actions ([95]); no sync generators

Verbs, one set for every language and host:
- `build`, `test`, `check`, `fix` on every project; `install` on every app and host project; `deploy` on infrastructure stacks; `upgrade` on every ecosystem root; `nx release` ships
- File-level formatting and linting belong to hk, project-level checking to the plugins, neither calling the other
- `check` fails on every project-level finding through each checker's own strict switch, cached on its inputs; `fix` writes the fixes that need a project model, uncached
- Each checker and writer is its own target (`check--<tool>`, `fix--<tool>`, `build--<tool>`); `check`, `fix`, `build`, `upgrade` are `nx:noop` aggregates over `<verb>--*` forwarding nothing (Nx would pass forwarded arguments to every dependency, [57]), their inputs the union of their members'; one-run arguments go to a tool-named target (`nx run <project>:build--dotnet -- -bl`), which function-hooks rewrites to
- Checkers come from what a project configures, never a fixed list; every finding is an error in each checker's own configuration; one diagnostic path per language; no build property flipping warnings into errors
- Distributables are `build` in its release configuration; shipping is `nx release` running each project's `nx-release-publish`
- `install` puts the current local build into its host through the host's own channel, no version or release; `upgrade` moves an ecosystem's dependencies through its own tool; `nx migrate` upgrades Nx

Nx through its own mechanisms: modes are target `configurations`, groups are `dependsOn` globs, scope is `affected`/`--files`/`-p`, one-run switches are arguments after `--` to a tool-named target; each plugin owns its targets whole. Entry points: `nx <verb> <project>` for one project, `nx affected -t <verb> --files=<path>` for a change's reach, `nx affected -t <verb>` for changed work (what CI runs), `nx run-many` deliberately; `hk check`/`hk fix` for files; `nx format` is not used.
