# Claude provider
Agent task: verify and raise the Relay Claude provider (swap trace, protocol and storage facts, lock verdict, quality), 2026-09-13.

**Swap verdict ("if I swap account, will it swap in claude cli?"): yes, when the app and the terminal see the same store (a–d); no when `CLAUDE_CONFIG_DIR` lives only in the shell (e).** Evidence is the installed `claude` 2.1.270 (`~/.local/bin/claude`, strings of the bun binary) and code.claude.com docs.
- (a) Fresh machine: `connect` runs `claude auth login --claudeai` with `CLAUDE_CONFIG_DIR=<private dir>`, so the browser login lands in `Claude Code-credentials-<hash>` and `<private>/.claude.json`; `select` finds no shared login, imports through `auth login` with `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`+`_SCOPES`(+`_CLIENT_ID`), which the binary handles as `grant_type=refresh_token` → save → `hasCompletedOnboarding` (`de`/`P7`/`afe`). CLI ends up signed in as the selected account; nothing is parked, so nothing strands.
- (b) A→B→A: works. B's login runs `oV(preserveInProcessTokens:true)`, so it never revokes A's parked refresh token; a native refresh of A between Relay's read and the import is excluded because Relay holds `.oauth_refresh.lock`, which Claude Code's refresh (`wm`) takes before every rotation. The way back parks B's rotated grant over B's stale private copy. Strand only if the finalizer exchanges the token and dies before saving; the journal then marks the incoming account unavailable (sign in again), as the README states.
- (c) Crash between park and import: journal holds `pending.phase == .prepared`, no child; `recoverAccounts` reconciles against the shared store (still A), clears pending, B keeps its unconsumed refresh token. Crash after the child started: pid+start-time identity decides; if the shared store is not B, B is marked unavailable, conservatively.
- (d) CLI open in a terminal: its refresh takes the same `.oauth_refresh.lock`, so Relay reports `leaseBusy` during a native refresh and a native refresh during a swap retries 5×1–2 s then stops without writing. After the swap the CLI's credential poll (`.credentials.json` mtime, else Keychain access-token compare) reloads, and its 401 path re-reads the store and adopts the new token (`tengu_oauth_token_refresh_race_resolved`) instead of refreshing A. In-flight requests keep their bearer. README claim holds.
- (e) `CLAUDE_CONFIG_DIR` in the shell only: the app's `ProcessInfo.environment` lacks it, so Relay targets `~/.claude` + `Claude Code-credentials` + `~/.claude.json` while the terminal reads `Claude Code-credentials-<sha256(dir)[0:8]>` + `<dir>/.claude.json`. The swap succeeds into a store the terminal never reads; nothing strands, the CLI stays on its old login. Cause is the environment source in `RelayStore.init` (not mine): resolve the login shell's value there.

**Lock verdict: real, both of them.** `oauthRefreshLockOptions` = `{lockfilePath: <store>/.oauth_refresh.lock, realpath:false, stale:60000, update:5000}` plus a legacy `${realpath(store)}.lock`; the secure-storage writer locks `<store>/.storage-write` (proper-lockfile → `.storage-write.lock`, `stale:15000`, retries 10, default update 7.5 s). `ClaudeRefreshLease` mirrors proper-lockfile exactly (mkdir, mtime staleness, utimes heartbeat, compromise on mtime/inode drift). The login save takes only the write lock, so holding the refresh lock during import is correct; the old comment naming a "storage-write lease" was right in effect and is now stated precisely.
