## Findings

1. **Location** lines 113-115, 129, 168 (`Typed.cs`, `Adapters.cs` in the lab).
   **Claim** "The codes live in one closed block, and a consumer classifies an error with `Is`, `HasCode`, or `IsType<E>`, never by its message text." with `Expected("The beneficiary BIC is invalid", 1)`, `Expected("Transfer date cannot be in the past", 2)`, and `result.Catch(1, _ => fallback).As()`.
   **Evidence** The sentence describes a closed block the file never shows. The codes are two bare literals declared inside the records, and the recovery site repeats a third bare `1`. The global ruling spells the form as "codes in one closed block", and `21-languageext-result-types.md` shows it as `Codes.InvalidAge`, `Codes.NotFound`. The prose is false about the file's own code.
   **Correction** In the "Typed business validation" block, before the records:
   ```csharp
   internal static class Codes {
       public const int InvalidBic = 1;
       public const int TransferDateIsPast = 2;
   }

   internal sealed record InvalidBic() : Expected("The beneficiary BIC is invalid", Codes.InvalidBic);

   internal sealed record TransferDateIsPast() : Expected("Transfer date cannot be in the past", Codes.TransferDateIsPast);
   ```
   In the "Adapting error types" block: `result.Catch(Codes.InvalidBic, _ => fallback).As()`. Mirror both edits in `F11/Typed.cs` and `F11/Adapters.cs` and rebuild.

2. **Location** lines 136-139 (host-only block).
   **Claim** `IActionResult BookTransfer(Request request) => Handle(request).Match<IActionResult>(...)`.
   **Evidence** `BookTransfer` is already a record declared at line 111 of the same file, so the method name shadows a type the file defines; the brief requires every identifier in a block to be the file's own or the assembly's. `Handle` is also unqualified while the file declares `Workflow.Handle` and `Handler.Handle`, and only `Workflow.Handle(Request)` returns the `Fin<Unit>` this `Match` consumes. The book's original had the same name for the method and the command type, so the collision is inherited, not introduced; the parameter type change makes the target ambiguous.
   **Correction** Replace the block with:
   ```csharp
   IActionResult Post(Request request) =>
       Workflow.Handle(request).Match<IActionResult>(
           Succ: static _ => Ok(),
           Fail: static error => BadRequest(error));
   ```

3. **Location** line 64.
   **Claim** "`Where` is not definable for `Fin<A>`. A false predicate must produce `Fail`, but a predicate supplies only `bool` and no `Error`."
   **Evidence** The book's version reads "not generally definable for `Either<L, R>` ... there is no universal empty value for arbitrary `L`". That reason does not carry over: `Fin` fixes the failure type to `Error`, and `LanguageExt.Common.Errors.None` is exactly the universal empty error (`public static readonly Error None = new ManyErrors(Seq<Error>.Empty)`). The assembly supports "no `Where` exists" (verified absent on `Fin_1`, `FinExtensions`, `FinGuardExtensions`, `Traits_Fallible`); it does not support "not definable".
   **Correction** "`Fin<A>` has no `Where`. A false predicate must produce `Fail`, but a predicate supplies only `bool` and no `Error`."

4. **Location** line 38.
   **Claim** "That is the shape every type in this file has."
   **Evidence** Added sentence; the painter passage ends at "unused and potentially inconsistent fields." The file also names `Option<T>`, whose cases are presence and absence rather than success and failure, and `IO<A>`, which the file itself describes as "a deferred effect", not a two-case container. The claim is false for two of the five types the file names.
   **Correction** "`Fin<A>` has that shape."

5. **Location** line 225 and the `Handler.Exit` block (lines 216-220).
   **Claim** "`Fail` with an `Expected` error or `ManyErrors`: expose actionable business errors."
   **Evidence** `Exit` returns a status code only, so the accumulated leaves never reach the caller. Nothing in the file shows how the promised business errors are read out of a `ManyErrors`. `Error.Filter<E>()`, `Count`, and `Head` are the members that do it (verified on `Common_Error`, and named in `21-languageext-result-types.md`).
   **Correction** Concrete gap, not a wrong sentence: a project adds the read-out at the same host `Match`, for example `error.Filter<InvalidBic>()` or `error.Count`, to build the client payload. Add one sentence after line 227 if the file should state it: "The host reads the accumulated leaves with `Filter<E>`, `Count`, and `Head` in the same `Match`."
