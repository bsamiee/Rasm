# [TS_UI_API_PERSPECTIVE_DEV_CLIENT]

`@perspective-dev/client` owns the millions-of-rows streaming-analytics engine: a WASM core holds appendable indexed `Table`s from which `View`s materialize, each maintained INCREMENTALLY as updates land. One `Client` API fronts an in-page `worker()`, a remote `websocket(url)` host, or a `VirtualServerHandler` over a foreign SQL source — data location is a wiring decision, never an API fork. Arrow is the wire: `Table` ingests IPC buffers, `View.to_arrow()` emits them, and `with_typed_arrays` lends decoded typed arrays with no copy.

- `TableInitOptions` carries the per-feed table modes: `index` upserts on the key column, `limit` ring-buffers rows, `page_to_disk` spills canonical data to a memory-mapped file (native) or OPFS (WASM Worker) past the memory ceiling, and `list_flatten` decides how Arrow `LIST` and JSON `Array` columns ingest — `zip` and `cartesian` expand one row per list element and are incompatible with `index`, `stringify` encodes each list as one JSON string column.
- Nested ingest is the engine's own: an Arrow `STRUCT` or JSON object expands recursively to one dotted column per leaf and a null parent nulls every descendant, so a feed hands its nested frame over whole. Under the default `zip`, every list column in one record shares a length and an empty list yields one null row — a ragged feed picks `cartesian` or `stringify`.
- `join` returns a LIVE reactive table re-deriving on either side's update; a hand-maintained merged copy beside it is the defect.
- `Client`, `Table`, and `View` each implement `[Symbol.dispose]()`, so a `using` binding releases the handle at scope exit and an explicit `delete()`/`terminate()` is the non-lexical path.
- `Client.__unsafe_open_view` re-opens a `View` by the raw id `View.__unsafe_get_name()` yields, the only route across a Worker boundary the handle wrapper cannot be cloned over; the caller guarantees the id names a live `View` on the connected server.

## [02]-[VIEW_PROTOCOL]

`ViewConfigUpdate` is the whole query surface; `expressions` validate through `Table.validate_expressions`, and `windows` declares rolling computations symmetric with them:

| [INDEX] | [FIELD]                                | [SHAPE]                      | [ROLE]                                     |
| :-----: | :------------------------------------- | :--------------------------- | :----------------------------------------- |
|  [01]   | `group_by` / `split_by`                | `string[]`                   | row pivots / column pivots                 |
|  [02]   | `columns`                              | `(string \| null)[]`         | projected columns, read positionally       |
|  [03]   | `aggregates`                           | `Record<string, Aggregate>`  | per-column aggregate, tuple form for deps  |
|  [04]   | `filter` + `filter_op`                 | `Filter[]` · `FilterReducer` | predicate rows and their reducer           |
|  [05]   | `sort`                                 | `[string, SortDir][]`        | the ONLY field ordering a `View`'s rows    |
|  [06]   | `expressions`                          | `Record<string, string>`     | ExprTK computed columns                    |
|  [07]   | `windows`                              | `Record<string, WindowSpec>` | ordered partitioned rolling computations   |
|  [08]   | `group_by_depth` / `group_rollup_mode` | `number` · `GroupRollupMode` | tree depth and row rollup presentation     |
|  [09]   | `split_rollup_mode`                    | `SplitRollupMode`            | column-group subtotal and grand-total emit |

`Filter` is `[column, operator, FilterTerm]` and `FilterReducer` is `"and" \| "or"`; `GroupRollupMode` is `"rollup" \| "flat" \| "total"` and `SplitRollupMode` is `"flat" \| "rollup"`.

`WindowSpec` keys one output alias: `column` names the input (a `Table` column or a same-config expression alias), `aggregate` the window function, `partition_by` the grouping tuple (empty partitions the whole `Table` as one group), and `order_by` a `[column, "asc"|"desc"]` pair ordering rows WITHIN the frame without reordering the `View`. Exactly one frame field applies — `rows` (preceding row count), `range` (an `order_by`-value band), or `cumulative` — with `offset` feeding `lag`/`lead`/`nth_value`/`ntile` and `alpha` the smoothing factor in `(0, 1]`. Each alias must clear every `Table` column, expression alias, and sibling window key, and a collision refuses the config.

Windows have NO pre-ship validator, and three refusals are therefore the consumer's to catch. `Table.validate_expressions` deserializes `Expressions` alone and answers nothing about `windows`; an alias collision refuses ENGINE-side only at `Table.view` build; the frame trio is mutually exclusive by the engine and NOT type-encoded, all three being independently optional on `WindowSpec`; and `Windows` is a JSON object, so DUPLICATE keys have already collapsed last-wins by the time a config value exists — a gate that must observe a repeat takes ordered entries. Engine refusals close the roster: `ema` accepts the cumulative frame alone, `rate` REQUIRES a `range` frame, `lag`/`lead`/`diff` take an `offset` and no frame at all, and a `range` frame needs a numeric or temporal `order_by`.

Aggregate roster (numeric): `sum` `abs sum` `sum not null` `avg` `mean` `count` `distinct count` `dominant` `first` `last` `last by index` `high` `low` `max` `min` `high minus low` `last minus first` `median` `q1` `q3` `pct sum parent` `pct sum total` `stddev` `var` `unique` `weighted mean` `min by` `max by`; string adds `join`; date/datetime and boolean carry the applicable subset. Window aggregates cover the framed folds (`sum` `avg` `count` `min` `max` `stddev` `var`), the offset family (`lag` `lead` `diff` `nth_value` `ntile`), the ranking family (`row_number` `rank` `dense_rank` `percent_rank` `cume_dist`), and the argument-taking `ema` (`alpha`) and `rate` (`range` frame).

Filter operators: the ordering and identity set (`==` `!=` `>` `<` `>=` `<=` `is null` `is not null`) applies to every type, and string columns add `begins with` `not begins with` `contains` `not contains` `ends with` `not ends with` `matches` `not matches` `in` `not in`, where `matches`/`not matches` take a regex term. Every virtual source declares its own per-type roster through `Features.filter_ops`, `Features.aggregates`, and `Features.window_aggregates` — each keyed by `ColumnType`, each `WindowAggSpec` carrying `name`, the `frames` it accepts (empty meaning no frame at all), whether it takes an `offset` or `alpha`, and a `result_type` whose absence means the source column's own type — read through the handler's `getFeatures()`.

[VIEW]: `View.to_arrow(ViewWindow?) -> Promise<ArrayBuffer>` `View.to_columns(ViewWindow?) -> Promise<object>` `View.to_columns_string(ViewWindow?) -> Promise<string>` `View.to_json(ViewWindow?) -> Promise<Array<any>>` `View.to_json_string(ViewWindow?) -> Promise<string>` `View.to_csv(ViewWindow?) -> Promise<string>` `View.to_ndjson(ViewWindow?) -> Promise<string>` `View.with_typed_arrays(TypedArrayWindow?,Function) -> Promise<void>` `View.on_update(Function,OnUpdateOptions?) -> Promise<any>` `View.remove_update(number) -> Promise<void>` `View.on_delete(Function) -> Promise<any>` `View.remove_delete(number) -> Promise<any>` `View.schema() -> Promise<any>` `View.expression_schema() -> Promise<any>` `View.get_config() -> Promise<any>` `View.dimensions() -> Promise<any>` `View.num_rows() -> Promise<number>` `View.num_columns() -> Promise<number>` `View.column_paths(ColumnWindow?) -> Promise<any>` `View.get_min_max(string) -> Promise<Array<any>>` `View.collapse(number) -> Promise<number>` `View.expand(number) -> Promise<number>` `View.set_depth(number) -> Promise<void>` `View.delete() -> Promise<void>`

- `View.with_typed_arrays(window, callback)`: declares `callback` as bare `Function` and calls it `(names: string[], values: TypedArray[], validities: (Uint8Array|null)[], dictionaries: (string[]|null)[]) => void | Promise<void>`. Those arrays borrow the Arrow buffer and stay valid ONLY for the callback's duration — the borrow ends at a synchronous return, or at SETTLEMENT when the callback answers a `Promise`, so an `await requestAnimationFrame` upload stays in bounds while a stashed reference reads freed memory.
- Null slots reach `values` ZERO-FILLED in place, so `validities` is the only absence evidence and a zero read as a datum is the defect; the call also FORCES `emit_legacy_row_path_names` to `false` whatever the window carries, so a group-by lane reads `__ROW_PATH_N__` here while a `to_*` serializer over the same `View` still defaults to the legacy spelling.
- `ViewWindow.emit_legacy_row_path_names` names group-by columns `"colname (Group by N)"` when true (the default) and `__ROW_PATH_N__` when false, matching the SQL backend.
- `TypedArrayWindow` extends `ViewWindow` with `float32`, which is NON-OPTIONAL on the type though the engine defaults it, so every window value spells it. `float32: true` narrows Float64 AND Int64 columns to `Float32Array` — the Int64 narrowing is undocumented — while Date32 and Timestamp DELIBERATELY stay `Float64Array`, because epoch milliseconds in f32 quantize to roughly a quarter second; a consumer expecting narrowed dates reads the wrong array class.

## [03]-[HOST_TOPOLOGY]

- Browser: `worker()` runs the engine in a dedicated/shared Worker off the UI thread; `init_server` registers the engine binary and `getCompiledClientWasm()` hands a spawned Worker a structured-cloneable module to self-instantiate its `Client` with no re-fetch.
- Bitness: `init_server(ServerWasmSource | { wasm32?, wasm64? })` registers the engine binaries; a `ServerWasmSource` may be a `Uint8Array`, `ArrayBuffer`, `Response`, `WebAssembly.Module`, a promise of those, or a `() => Promise<ArrayBuffer | Response | WebAssembly.Module>` THUNK, and only the thunk form guarantees the losing bitness never downloads. Selection and download DEFER to the first `worker()` call; a registration carrying neither key throws.
- Selection: `wasm64` is taken when it is registered and either no `wasm32` stands beside it or `host_supports_memory64()` holds — so a LONE `wasm64` is used regardless of the probe and fails at instantiation on an unsupporting host, which is the correct error for an explicit opt-in. Selection falls back to `wasm32` behind a `console.warn` when a chosen `wasm64` fails to load and `wasm32` is also registered, and otherwise rethrows. `host_supports_memory64()` is a memoized `WebAssembly.validate` over the encoding of `(module (memory i64 1))`, the same probe `wasm-feature-detect` uses.
- Memory64 is a REAL second binary — `@perspective-dev/server` ships `perspective-server.memory64.wasm` beside `perspective-server.wasm`, its memory maximum 262144 pages against the wasm32 engine's 65536, raising the heap ceiling from 4GB to 16GB at some engine performance cost; registering `wasm32` alone opts out.
- Node: `PerspectiveServer` (with `make_session` / `make_client`) and the `WebSocketServer` adapter publish named `Table`s over `ws`; a browser client attaches through `websocket(url)` then `open_table(name)`, and every client's `View`s update incrementally off the server's indexed feed. `WebSocketServer` is a reference integration carrying no authentication, authorization, origin enforcement, or rate limiting.
- Virtual servers: a `VirtualServerHandler` answers the protocol over any foreign source, `createMessageHandler` binds it to a `MessagePort`, `VirtualDataSlice` accepts the typed column writes, and `Features` declares which pivots, filter operators, aggregates, and window aggregates that source supports. `./virtual_servers/duckdb` ships `DuckDBHandler` over `@duckdb/duckdb-wasm` and `./virtual_servers/clickhouse` ships `ClickhouseHandler`; `GenericSQLVirtualServerModel` builds the SQL a custom handler executes.

## [04]-[IMPLEMENTATION_LAW]

[TOPOLOGY]:
- `validate_expressions` declares `Promise<any>` and the distribution ships no typed verdict, so a consumer DECODES the report rather than asserting it — refusals ride an `errors` map keyed by expression alias whose value carries the engine's own `error_message`, the accepted half rides `expression_schema`, and `expression_alias` carries the retained aliases; asserting that shape as a type reads a record the package never promised.
- `Table.get_name` and `Table.get_client` answer a `Promise`, so every table identity read awaits the engine round trip like the rest of the handle surface.
- `group_rollup_mode: "total"` and a non-empty `group_by` cannot both hold: the engine logs the conflict and silently coerces the side the update did not assert, so a config asserting both reads back changed. `split_rollup_mode` carries no `total` — an empty `split_by` already is the single grand-total column group — and it defaults to `"flat"` where `group_rollup_mode` defaults to `"rollup"`.
- `windows` is the ONE query field with no validation route before a `View` opens, so its alias, frame-exclusivity, and `alpha`-bound checks belong to the consumer; borrowing the expression gate for them validates nothing, and the consumer catches a duplicate alias before the object literal erases it.
- Engine registration is module-global and one-shot in effect: `init_server` resets the resolved binary, so a second call after the first `worker()` has selected swaps the engine under a live client — the boot belongs to one explicit owner, never an import side effect.

[STACKING]:
- `apache-arrow`(`.api/apache-arrow.md`): one columnar format end to end — a wire Arrow frame feeds `Client.table(buf,{format:"arrow",index})`, `Table.update(arrowBuf)` appends deltas, and `View.to_arrow()` hands results to `tableFromIPC` for any Arrow consumer; `with_typed_arrays` skips the `Table` materialization entirely where the consumer wants raw buffers, never a JSON re-materialization between engines.
- `@effect-atom/atom-react`(`.api/effect-atom-atom-react.md`): each handle is a `Scope`-bracketed resource with explicit `delete()`; `on_update`/`on_error` bridge into streams at the async seam and their `remove_update`/`remove_delete` ids are the unsubscribe the bracket releases, and a rendered surface's `ViewConfigUpdate` derives from an atom — a config change creates a new `View` and deletes the old.
- `@perspective-dev/viewer`(`.api/perspective-dev-viewer.md`): the viewer element consumes this client's `Table` via `load()` and drives its own `View` lifecycle; headless consumers (exports, alerts, derived feeds) hold `View`s directly.
- `@tanstack/react-table`(`.api/tanstack-react-table.md`): boundary — the `Grid` fold owns interactive accessible grids over client-modeled rows, perspective owns engine-scale streaming pivot/aggregation over a feed; derivation locus decides, client-modeled rows to `Grid` and engine-maintained aggregates to perspective, one surface never both.
