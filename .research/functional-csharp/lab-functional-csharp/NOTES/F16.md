# F16 notes: stateful computations

Lab `Lab.F16` builds with zero diagnostics and runs with exit 0. Every `csharp` block of the doc is a contiguous span of a lab file.

## Members verified

- `State<S, A>` positional record constructor `new(Func<S, (A Value, S State)>)` as `NextInt` and `GetAndIncrement`; a `{ get; } = new(static ...)` property initializer target-types the constructor.
- `State<S, A>.Run(S) : (A Value, S State)`; the tuple compares with `==` against `(5, 6)` and deconstructs into a named tuple local.
- `State<S, A>.Map(Func<A, B>)`, `Select`, `SelectMany` (LINQ with two `from` clauses, a conditional `empty ? Empty : NonEmpty` source, and a recursive property source that stays lazy inside the bind lambda).
- `State.gets<S, A>(Func<S, A>)`, `State.pure<S, A>(A)`, `State.modify<S>(Func<S, S>)` : the pure cache. Type arguments are explicit: `gets<S, A>`, `pure<S, A>`, `modify<S>`.
- `StateT<S, M, A>.Run(S) : K<M, (A Value, S State)>`, then `.As()` to `IO<(...)>` and `RunSafe()` to `Fin<(...)>`.
- `StateT.get<M, S>()`, `StateT.pure<S, M, A>(A)`, `StateT.put<M, S>(S)`, `StateT.modify<M, S>(Func<S, S>)`, `StateT.liftIO<S, M, A>(IO<A>)`. The type-argument order differs per function: `get`/`put`/`modify` take `<M, S>`, `pure`/`liftIO` take `<S, M, A>`.
- `StateT<S, IO, A>.SelectMany(Func<A, IO<B>>, ...)`: `from value in fork.Await` binds a bare `IO<B>` inside a `StateT` query.
- `StateT<S, IO, A>` failure: `IO.fail<decimal>(new RateUnavailable())` inside the lifted fetch surfaces as `Fail` from `RunSafe()` with `HasCode(1600)`; the hit path never runs the failing fetch.
- `Option<A>.Match(Some: static ..., None: () => ...)` with both lambdas returning `State<S, A>` (and `StateT<S, IO, A>`) infers `B` without a type argument; the `Some` lambda parameter must not reuse the query's range variable name.
- `HashMap<string, decimal>()` empty from `Prelude`, `HashMap(("USDEUR", 3m))`, `Find`, `Add`.
- `Stateful.state<State<int>, int, int>(Func<int, (int, int)>) : K<State<int>, int>` then `.As()`; `State<S>` implements `Stateful<State<S>, S>`.
- `Stateful.local<State<int>, int, int>(Func<int, int>, K<State<int>, int>)`: runs the operation on the modified state and restores the prior state (`Run(1)` returns `State == 1` while the value equals `NextInt.Run(101).Value`).
- `IO<A>.Fork()` lifted through `StateT.liftIO<int, IO, ForkIO<int>>` and `ForkIO<A>.Await` bound as `IO<A>`: the parent state threads normally around the fork.
- `AtomHashMap<string, int>` with `SwapKey(key, Func<Option<V>, Option<V>>)` and `Find` as the fetch call counter (`Atom<int>` with a `_` lambda parameter collides with the `_ =` discard, CS0029).
- `head.Cons(tail)`, `Seq<int>()`, `Option<int>.None` in a `select` conditional, `Some(value)`.
- Generic records `Tree<T>`, `Leaf<T>`, `Branch<T>` with an abstract `Number()` on the base and a non-generic static `Tree` factory so `Map`/`select` infer `Tree<...>` rather than `Leaf<...>`; `==` between two `Tree<(int Number, string Value)>` values is structural.

## Corrections to the plan and the article

- CORRECTION (article `state-transformer-11.md`, "Forked state"): the installed build cannot fork a `StateT<S, IO, A>`. `StateT<S, M>` implements only `Maybe.MonadUnliftIO` and `Maybe.MonadIO`, not `MonadUnliftIO<M>`/`MonadIO<M>`, so `Prelude.fork`, `ForkIO`, `ForkIOMaybe` (extension) all fail CS0311. Calling the static virtual `M.ForkIOMaybe(ma)` through a helper constrained to `Maybe.MonadUnliftIO<M>` compiles and throws at construction: `ExceptionalException` "The IO monad is not in the monad-transformer stack or MonadIO.ToIO has not been implemented" (`StateT<S, M>` does not override `ToIOMaybe`). The lab keeps this as `Try.lift(() => ForkAndAwait(increment).As()).Run().IsFail`. The doc states the fact instead of the article's copy-and-diverge behavior.
- The plan's `liftIO` alternative: only `StateT.liftIO<S, M, A>` and `StateT<S, M, A>.LiftIO` exist; `Prelude` has no `liftIO`. The doc names `StateT.liftIO`.
- The plan's `State.get`/`gets`/`put`/`modify` module functions exist with those spellings; the doc uses `gets` and `modify` on `State`, `get` and `put` on `StateT`, so all four compile.
- `Return` becomes the module `State.pure<S, A>`; the Prelude `Pure(x)` implicit lift also converts to `State<S, A>` where a target type exists, but `Option.Match` branches have none, so the doc shows one spelling.
- `Fin<(int, int)> == Pure((42, 1))` compiles and holds.
