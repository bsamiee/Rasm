# F16 review: 16-stateful-computations.md

1. Fabricated identity claim about Parsec
- Location: line 217, last sentence of "Generalizing beyond integer seeds".
- Claim: "`LanguageExt.Parsec` is `State` over its input."
- Evidence: `ilspycmd -t 'LanguageExt.Parsec.Parser`1' ~/.nuget/packages/languageext.parsec/5.0.0-beta-77/lib/net10.0/LanguageExt.Parsec.dll` yields `public delegate ParserResult<T> Parser<T>(PString input);`. `Parser<T>` is a delegate from `PString` to `ParserResult<T>`; it is not `State<S, A>` and does not use it. `NOTES/F16.md` records the sentence as "named without a lab witness".
- Correction: replace with "`LanguageExt.Parsec` follows this model: its `Parser<T>` maps a `PString` to a `ParserResult<T>` that carries the unconsumed input."

2. Unsupported short-circuit claim for an `Option` produced value
- Location: line 90, "Stateful computations".
- Claim: "The produced value can itself be an `Option<A>`. The state then survives while value transformations short-circuit on `None`: the bind preserves the state and delegates transformation of the value to `Option.Bind`, and the final consumer still pattern-matches the inner option at the boundary."
- Evidence: `sigs/State_2.txt` lists `Bind<B>(Func<A, K<State<S>, B>>)`, `Bind<B>(Func<A, State<S, B>>)`, and the `Gets`/`Put`/`Modify` overloads only. `State<S, Option<A>>` passes the `Option<A>` through as an ordinary value; no overload consults `Option.Bind` and nothing short-circuits. The file's own `OptionInt` (line 141) is a plain `State<int, Option<int>>` whose seed advances on every bind. The short-circuit behavior belongs to `OptionT`, which this file does not name, and under `StateT<S, OptionT<IO>, A>` a `None` discards the state instead of preserving it. No lab probe covers the claim; `NOTES/F16.md` lists none.
- Correction: replace the two clauses with "The produced value can itself be an `Option<A>`, as `OptionInt` shows: the seed advances on every bind and the consumer matches the option at the boundary. The produced value can also be a function, so a stateful computation can thread behavior as well as data."

3. `State.modify` explained twice
- Location: line 34 and line 92.
- Claim: line 34 "`State.modify` replaces the state with a function of it"; line 92 "`State.modify` applies a function of shape `S -> S` to the state, and `State.put` replaces it, both with `Unit` as the produced value."
- Evidence: `sigs/State.txt` lines 27 and 32 give `State<S, Unit> put<S>(S)` and `State<S, Unit> modify<S>(Func<S, S>)`; both statements are true, so the second repeats the first fact. The brief forbids restating one fact twice in a file.
- Correction: line 92 becomes "`State.put` replaces the state, and it and `State.modify` both produce `Unit`. The module functions take explicit type arguments."

- Location: line 70, end of "Separate state mutation from other effects".
- Claim: "`Run(state)` on a `StateT` returns `K<IO, (Value, State)>`, and the host converts it with `.As()` and exits through `RunSafe()`."
- Evidence: `sigs/StateT_3.txt` line 442 confirms `Run(S) : K<M, (A Value, S State)>`. The sentence stops at `RunSafe()`, so a project built on the file has no statement of what the host does with the `Fin<(decimal, HashMap<string, decimal>)>` that comes back; `NOTES/F16.md` lists that host `Match` as still needed.
- Correction: append one clause to the same sentence: "`Run(state)` on a `StateT` returns `K<IO, (Value, State)>`, the host converts it with `.As()`, exits through `RunSafe()`, and matches the resulting `Fin` into its own vocabulary."
