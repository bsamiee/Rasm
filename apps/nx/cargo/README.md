# @rasm/nx-cargo

Nx plugin for Cargo workspaces. It reads each workspace through one `cargo metadata --format-version 1 --no-deps` call (`--no-deps` reads no lock, index, or crate) and its `Cargo.lock`, and infers a project per member with targets that run the commands a terminal runs from the workspace root.

## [01]-[SETUP]

```json
{ "plugins": ["@rasm/nx-cargo"] }
```

No plugin options exist, since Cargo's own configuration states every fact it reads: `build.target-dir` and `build.build-dir` place output, `rust-toolchain.toml` picks the toolchain, `[profile.*]` tables name build configurations and panic strategies, `clippy.toml`, `.config/nextest.toml`, `[workspace.metadata.dylint]`, and `deny.toml` decide which checkers run. Under CI (Nx `isCI()`), compile and publish commands add `--locked`.

Checkers select from each package's targets in `cargo metadata`, every kind but examples, as Dylint's own lint pass does: `--lib` for a library target, `--bins` for a binary, `--tests` where a target sets `test`, `--benches` for a bench target (metadata states no `bench` flag, and a library or binary built as a benchmark compiles the same `cfg(test)` code `--tests` reaches), so a binary-only crate never meets cargo's `no library targets found`; a Dylint library keeps its lint fixtures as `[[example]]` targets, the form that gives fixtures the package's dev-dependencies, and `--fix` over them would rewrite the fixtures; `cargo test` and nextest still compile every example. Each profile whose `panic` strategy differs from `dev` adds one checker run under `--profile <name>`: Cargo passes a profile's `-C panic` to every crate it builds except test harnesses, so `cfg(panic = "abort")` code compiles under that profile alone.

`build--cargo` declares the files cargo uplifts into the target folder for the running configuration (`{options.outputs.<n>}`, since Nx reads no `outputs` inside a configuration): binaries and every library crate type but `lib` and `rlib`, which a nightly cargo writes to the build folder alone (`uplift_to` in cargo's `compilation_files.rs`).

Every task of one command runs in one cargo process (`preferBatch`), selecting each package by package ID spec, so Cargo takes its build-directory lock once and unifies features across the selection. Each task takes its result from its own package's report: compile commands read cargo's JSON messages (an `error` fails the package, a `compiler-artifact` proves it built), `cargo nextest run` reads nextest's `libtest-json-plus` suites per package (format version `0.1`, enabled through `NEXTEST_EXPERIMENTAL_LIBTEST_JSON=1`, nextest's documented switch), and `cargo test` and `cargo deny` take the exit status alone. A task whose package depends on a package that failed is skipped, as is a task with no report while another package failed; a package with no nextest suite in a finished run with no failed test fails with `no tests to run`, as its direct run exits; with no failure named, every unreported task fails with the whole log. Lint levels come from `[lints]` alone: a level of `deny` makes a finding an error, so no warning rule sits in the plugin. Green tasks cache however many others fail. Edges are `implicit`; external nodes `cargo:<name>@<version>` carry the lock checksum (or Git source) as their hash, so a lock change reruns only the projects reaching the moved package.

`upgrade--cargo` moves every requirement cargo-edit treats as unpinned: requirements holding `=`, `<`, `<=`, or `*`, and renamed dependencies, stay, so a hold reads `">=x.y.z, <next"` and `cargo update` still takes patch releases inside it. cargo-edit moves a requirement to a prerelease only when it already names one, and leaves Git dependencies to `cargo update`.

## [03]-[RELEASE]

Publishable members (a `version` and no `publish = false`) get the `release` tag, which `nx.json` selects, and `release.version.versionActions: "@rasm/nx-cargo/release/version-actions"`, which writes `[package] version` or the inherited `[workspace.package] version`, rewrites every requirement on a released member (dependency tables, target tables, `[workspace.dependencies]`) keeping its operator and the file's layout, and refreshes each `Cargo.lock` with `cargo update --workspace` unless `release.version.versionActionsOptions.skipLockFileUpdate` is set. Writes go to the manifests Nx resolves from `manifestRootsToUpdate` (the member's own `Cargo.toml` by default). A member inheriting `version.workspace = true` shares one version with every other inheriting member, so it versions in a fixed release group; an independent group fails naming the project. The registry version is the highest SemVer the crates.io index holds that is not yanked.
