# REVIEW F18 — `18-async.md`

1. **Location** line 13, `## Task<T> as an effectful container`.
   **Claim** "`IO<A>` is the effect type for the workflow: it wraps a `Func<Task<A>>`, and each run creates a fresh task."
   **Evidence** `IO_1.cs:31` — `public abstract record IO<A> : K<IO, A>, Monoid<IO<A>>, Semigroup<IO<A>>`. It holds no delegate field. The concrete cases are DSL records (`IOPure`, `IOBind`, `IOApply`, `IOLiftAsync`, `IOTail`), and `RunAsync(EnvIO)` (`IO_1.cs:896`) walks them in a loop. Only `IO.liftAsync` stores a task-returning function: `IO.cs:154` returns `new IOLiftAsync<A, A>((EnvIO _) => f(), pure)`. A pure or synchronous `IO<A>` creates no task at all.
   **Correction** replace the clause with: `` `IO<A>` is the effect type for the workflow: `IO.liftAsync` holds the `Func<Task<A>>`, and each run calls it again. ``

2. **Location** line 152, `## Traversing tasks`.
   **Claim** "Parallel traversal forks one thread per element, so a large collection is chunked and each chunk is traversed in turn."
   **Evidence** `Seq<A>.Traverse<F, B>` (`Seq.cs:739`) calls `Traversable.traverse`, and `Traversable<Seq>.Traverse` folds with `Applicative.lift(add, state, f(value))`. `Applicative.lift` is `F.Pure(f).Apply(fa).Apply(fb)` (`Traits_Applicative.cs:391`), and `Applicative<IO>.Apply` reaches `IO<A>.ApplyBack` → `new IOApply<A, B, B>(...)` (`IO_1.cs:102`). `IOApply.Invoke` runs `Ff.RunAsync(envIO)` then `Fa.RunAsync(envIO)` and awaits afterwards. No `Task.Factory.StartNew`, no thread. Only `Fork` allocates a thread (`IO_1.cs:463`, `TaskCreationOptions.LongRunning`). The lab used `IO.pure` operands, so it never exercised the async path and did not prove the thread claim.
   **Correction** `Parallel traversal starts every element effect before it awaits any of them, so a large collection is chunked and each chunk is traversed in turn.`
   **Coherence** `23-languageext-traits-and-transformers.md:232` carries the same wrong cell ("parallel and unbounded, one thread per element"), and the BRIEF traversal row repeats it. Fixing F18 alone makes the two files disagree; this belongs to the coordinator.

3. **Location** line 115, `## Data dependency determines sequencing or parallelism`.
   **Claim** "`Fork` starts one effect on its own thread and returns a `ForkIO<A>` whose `Await` yields the value, and `awaitAll` does the same for a `Seq<IO<A>>`. Each fork takes one dedicated thread, so a large fan-out is bounded by chunking the collection before traversal."
   **Evidence** `Prelude.awaitAll<A>(Seq<IO<A>>)` (`Prelude.cs:3582`) is `IO.liftAsync(async eio => (await Task.WhenAll(ms.Map(io => io.RunAsync(eio).AsTask()))).ToSeqUnsafe())`. It forks nothing and allocates no thread; only the `Seq<ForkIO<A>>` and `Seq<IO<ForkIO<A>>>` overloads await forks. `22-languageext-effects.md:110` states the neutral form ("`awaitAll` runs every effect of a `Seq` and collects the values"), so the doc contradicts file 22 as well.
   **Correction** `` `Fork` starts one effect on its own thread and returns a `ForkIO<A>` whose `Await` yields the value. `awaitAll` starts every effect of a `Seq<IO<A>>` and collects the values in order. Each fork takes one dedicated thread, so a large fan-out through `Fork` is bounded by chunking the collection first. ``
