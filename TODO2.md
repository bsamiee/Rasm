## [02]-[RULES]

- Every tool, language, format, field, and schema takes its newest release, no legacy form (`project.pbxproj`, `createNodesV2`, deprecated keys)
- Files start from the owning tool's generator (`mise use`, `pnpm init`, `nx init`, `nx add`, `swift package init`, `cargo init`, `uv init`, `dotnet new`), edited only where a fact differs
- `nx.json` stays plain: plugin rows and one-line entries, no root shell targets, no multi-line commands, no per-tool entry points
- Projects expose one `build`, `test`, `lint`, `format`, and `check` each, the plugin choosing the tool behind them, never `lint:<tool>` or `format:<tool>` rows
- One plugin per host or language, never a plugin mixing hosts the way `tools/nx` did
- Plugins copy the structure of official Nx plugins (`@nx/gradle`, `@nx/dotnet`, `@nx/js`, `@nx/vite`) and the Nx authoring docs (`docs/research/nx/`), nothing guessed
- Plugins are TypeScript where Nx calls them (`createNodes`, `createDependencies`, generators, version actions through `@nx/devkit`); work past that runs in a native core: Rust through napi-rs by default, the host's language where its API is native (MSBuild for .NET, `XcodeProjectFormat` for Xcode)
- Incremental tools keep their own incrementality (Cargo, SwiftPM, MSBuild), Nx caches only work the tool does not, inference runs one tool call per workspace cached by input hash
- Plugins are professional packages: minimal code, tested, documented, versioned, and published once complete
- Red state is accepted while each part is rebuilt in order
