## Corrections and confirmations

- `guard(flag, new AccountNotActive())` without the type argument infers `Guard<AccountNotActive, Unit>`, and `ToFin` fails with CS1929 (`FinGuardExtensions.ToFin` requires `Guard<Error, Unit>`). `guard<Error>(...)` is the spelling in both chains. Matches the F21 correction in `LAB-NOTES.md`.
- `Seq<Event>.Empty` does not resolve: the static import of `Prelude` binds `Seq<Event>` to the method `Prelude.Seq<A>()` (CS0119). The empty sequence is spelled `Seq<Event>()`.
- The plan's `history.Head.Map(static head => history.Tail.Fold(Create(head), Apply))` does not compile: `Head` is `Option<Event>` and `Create` takes `CreatedAccount`. The compiled form binds the head first: `history.Head.Bind(static head => head is CreatedAccount created ? Some(created) : Option<CreatedAccount>.None).Map(created => history.Tail.Fold(Create(created), Apply))`. A history whose first event is not a creation event rebuilds to `None`. The `Map` lambda captures `history`, so it is not `static`.
- The plan's `Choose(static e => e is DepositedCash d ? Some(row) : None)` needs `Option<StatementRow>.None` on the `None` arm. The lab uses `Switch<Option<StatementRow>>` with the explicit `None`, which names all four event cases in one pass.
- The row's "`guard` for the general-form check" runs inside the `IO` query, not in a separate `Validation` step. A rejected amount fails the effect before `Load` runs, and the store is unchanged.
- A rejected transition leaves the store unchanged: the sample reads `store.Value.Count` before and after a rejected `Handle` and both read the same count.
- `Apply` uses the state overload of the generated `Switch`: every case has an arm, so no discard arm and no throw exist, and the `createdAccount` arm returns the state unchanged (a replayed creation event is checked to leave `Currency` as it was).
- `AccountStatus` needs explicit enum values (RCS1161), the same ruling as F03's `Risk`.

## Host-only and uncompiled blocks

- The `text` fences (`Create`/`Fold` notation, the arrow signatures, the CQRS flow diagram) are notation.
- No block is host-only. The event store is an in-memory `Atom<Seq<Event>>`; the prose on relational, document, and specialized event databases stays conceptual with no code.
- Publishing has no code block: the handler ends at `Save`, and the "Persisting and publishing" prose covers publication.

## What a project built on this file still needs

- A real event store behind `Load` and `Save` with the same `IO` signatures, plus a durable subscription for publication.
- A `Validation<Error, MakeTransfer>` boundary that admits the raw command form (currency, beneficiary, amount) before the handler runs; the lab checks only the amount with `guard`.
- Time filters on the query side: the events carry no timestamp, so the period fold in the prose has no code.
- Optimistic concurrency on `Save` (expected version) if two handlers can debit the same account: `SwapIO` serializes appends but does not detect a stale decision state.

## Integration changes

- `Event` is a `[Union]` record: `TTRESG043` rejects a primary constructor on the base, so `AccountId` moves to a private constructor and the positional cases pass it up.
- `Account.Apply` and `Queries.Rows` call the generated `Switch`; `Switch(state, ...)` infers `AccountState` without type arguments, and `Rows` names `Switch<Option<StatementRow>>`.
- The case names are qualified (`Event.CreatedAccount`, `Event.DebitedTransfer`) in `Create`, `Rebuild`, `ToEvent`, and the samples.
- Prose: the event sentence, the transition sentence, and the pattern matching paragraph's third sentence name the union and `Switch`.
- `Samples.cs`: one check added (a replayed creation event leaves the rebuilt state unchanged).
