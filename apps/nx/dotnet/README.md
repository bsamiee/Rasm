# [NX_DOTNET]

`@rasm/nx-dotnet` is an Nx 24 plugin for MSBuild projects, forked from `@nx/dotnet` 24.0.5. One MSBuild evaluation of the workspace states every project, edge, input, and output, and each target runs the `dotnet` command a developer would type.

## [01]-[USE]

```json
{ "plugins": ["@rasm/nx-dotnet"] }
```

The plugin takes no options; Nx's own `targetDefaults` entries with `filter: { "plugin": "@rasm/nx-dotnet" }` override any inferred target field.

- Facts MSBuild's own files state are read back, never options: `ArtifactsPath` in `Directory.Build.props` places every output, `global.json` selects the SDK and the test runner, `NuGet.config` the package sources, `.editorconfig` the style rules
- A project whose evaluated `SupportedPlatform` items (the platforms the SDK's platform compatibility analyzer reads) leave out any of macOS, Linux, or Windows carries `os:darwin`, `os:linux`, or `os:win32` for each one it keeps, so a CI job selects the projects its runner can build; the SDK's default set states all three and adds no tag
- Every packable or publishable project carries the `release` tag, so `nx.json` selects .NET releases with `tag:release` in `release.projects`, since `nx release` selects npm libraries alone by default
- Version actions write `<Version>` through MSBuild's own project writer (`MsbuildAnalyzer version <version>`, the project text on stdin, `ProjectRootElement` with formatting preserved), into the last unconditioned `<Version>` or the first unconditioned `<PropertyGroup>`; the registry version is the highest SemVer `dotnet package search` lists across every source
- Version actions move every `AnalyzerReleases.Unshipped.md` row into its `AnalyzerReleases.Shipped.md` under `## Release <major>.<minor>.<patch>` on a stable release (Roslyn reads the header through `System.Version`, which holds no prerelease, so prereleases leave the rows unshipped), for the pair the project lists as `AdditionalFiles` and for the pairs of every project in its reference closure that ships through it (closure stopping at a packable or publishable reference, which releases its own)
- Version actions write no dependency rows: a `<ProjectReference>` carries no version, `dotnet pack` writes the referenced project's `<Version>` as the floor, and `nx release` raises every dependent on a `static` edge by a patch when a dependency moves (`updateDependents: "always"`)
- `#analyzer` names `analyzer/dist/MsbuildAnalyzer.dll` in the workspace and in the published package alike; the analyzer project states `Release` as its one configuration and that folder as its `Release` `OutputPath`, since npm packs only files inside the package and `tsc` keeps the package's own `dist`; a `static` edge from the package manifest to `MsbuildAnalyzer` (the project whose outputs hold the `#analyzer` file) makes `nx build @rasm/nx-dotnet` and the release build refresh the core, and the package's `prepare` (`dotnet build analyzer --configuration Release`) builds it in a fresh clone, where no graph exists before the core does; inference never builds anything and a half-saved MSBuild file in the tree cannot stop the graph

|  [02]   | `check--dotnet-build`              | Reads the SARIF 2.1 report `build--dotnet`'s compile wrote (`ErrorLog` in `Directory.Build.targets`, one per evaluation under its `IntermediateOutputPath`) and fails on each result at level `warning` or `error` with no `suppressions`, printed as `file(line,col): level id: text`                                                                                                                      | Every project               |   Yes   |

|  [04]   | `check--dotnet-format`             | `dotnet format style --no-restore --verify-no-changes`, batched into one run over the selection, the IDE rules no build runs included                                                                                                                                                                                                                                                                      | Every project               |   Yes   |
|  [05]   | `fix--dotnet-format`               | `dotnet format style`, then `dotnet format analyzers`, batched into one run each over the selection                                                                                                                                                                                                                                                                                                        | Every project               |   No    |
|  [06]   | `upgrade--dotnet`                  | `MsbuildAnalyzer upgrade <central file>`, then `dotnet restore --force-evaluate` over a traversal project of the projects reading it                                                                                                                                                                                                                                                                       | Central package folder      |   No    |
|  [07]   | `build`, `check`, `fix`, `upgrade` | `nx:noop` over every `<verb>--*` target, inputs `...` and the union of theirs                                                                                                                                                                                                                                                                                                                              | A `<verb>--*` target exists |   No    |
|  [08]   | `nx-release-publish`               | `dotnet pack <project>` (the configuration `PackRelease` selects), then `dotnet nuget push --skip-duplicate`, the key never on its command line: NuGet reads `NUGET_API_KEY` from the environment, then the source's `apikeys` entry in `NuGet.config`; in GitHub Actions, trusted publishing's `NuGet/login` step exchanges the job's OIDC token for a short-lived key the job exports as `NUGET_API_KEY` | Packable projects           |   No    |

- `build--dotnet` depends on `^build--dotnet`, so Nx batches a project with its references; the batch writes a traversal project outside the workspace whose `RestoreGraphProjectInputItems` restore every selected project in one NuGet graph and whose `Dispatch` target builds each project through a self-call, so MSBuild orders the projects by `ProjectReference` in one process and `-t:Dispatch -getItem:Built` reports each project's own result; a failed restore skips `Dispatch` and the item list comes back empty, where `-getTargetResult:Dispatch` throws `KeyNotFoundException` and kills the MSBuild server the run sat on; a task's output holds the diagnostics that name its project file, a failed task the whole log
- `build--dotnet` caches like `@nx/dotnet`'s `build`, on `NUGET_PACKAGES` and the absolute workspace folder too, since restore and `obj` files embed both; Nx restores outputs with their modified times and leaves matching outputs in place, so MSBuild's own up-to-date checks hold after a replay
- `check--dotnet-build` compiles nothing: the compiler writes every unsuppressed and source-suppressed diagnostic above `hidden` to the `ErrorLog` file whether or not `CoreCompile` is up to date on the next run, so the report holds the findings a replayed warning would miss, and one project has one writer; its inputs are the plugin's source and the `*.sarif` files among `build--dotnet`'s outputs, so Nx replays it while the report is unchanged; MSBuild's own warnings fail the build itself through `MSBuildTreatWarningsAsErrors` in `Directory.Build.props`, since the compiler's report never holds them
- `check--dotnet-format` and `fix--dotnet-format` depend on `build--dotnet`, whose run restores the project they read with `--no-restore`
- `upgrade--dotnet` moves each `PackageVersion` and `GlobalPackageReference` holding a plain version to the highest listed version across the sources `NuGet.config` and its package source mapping name, prereleases included; a range (`[x]` holds), a property, and an `Update` row stay; the edit rewrites the version text alone and keeps every comment column
- Targets the plugin's own executor runs hash the plugin's source, since Nx 24 hashes only `@nx/` executor packages: in the workspace that holds it (its manifest a tracked workspace file) through `{ "input": "default", "projects": ["@rasm/nx-dotnet"] }`, installed from npm through `{ "externalDependencies": ["@rasm/nx-dotnet"] }`, the package's external node
- A publishable project publishes in every configuration, since its distributable is the publish folder and a host install takes the build of the configuration the run names; its project references build inside that run under `_IsPublishing`, a build no other task produces
- Arguments after `--` reach the `dotnet` command when given to the tool-named target (`nx run <project>:build--dotnet -- -bl`); aggregates forward none, since Nx would pass them to every dependency's members too
